日期：2026-09-12（v4，已根据参考截图与多轮修订确定播放器/导航壳层方案）
状态：**已确认**，待按阶段转入实现计划（`docs/superpowers/plans/`）

## 1. 背景

Melodia 目前是纯手机形态的 Compose 应用：

- `AndroidManifest.xml` 中 `MainActivity` 写死 `android:screenOrientation="portrait"`，横屏从未被系统允许过。
- 没有任何 `sw600dp`/`-land` 等尺寸限定符资源，代码里也没有 `WindowSizeClass` 或类似的断点判断逻辑。
- 17 个 feature 模块全部是单栏手机布局，底部固定 `MelodiaNavigationBar`（首页/搜索/音乐库/创建 四个入口）+ 悬浮 `MiniPlayerCard`。
- 全屏播放器 `FullPlayerScreen` 及其歌词视图 `FullScreenLyricsView`、MV 播放页 `ArtistMvPlayerScreen` 均为高度定制的竖直堆叠布局（封面/歌词在上、控件在下），点开后整屏覆盖。
- 已有自建的设计 token：`core/ui/theme/Spacing.kt`（`MelodiaSpacing.xxs~xl`）、`Color.kt`、`Motion.kt`、`Shapes.kt`，以及一套 `Melodia*` 前缀的通用组件。

有利条件：`MainActivity` 已声明 `android:configChanges="orientation|screenSize|screenLayout|smallestScreenSize|keyboardHidden"`，解锁横屏后旋转/窗口尺寸变化不会重建 Activity，Compose 只需响应 `LocalConfiguration` 重组即可。

## 2. 范围（已与用户确认，含一次重大修订）

### 2.1 本次做的事

- 建立断点体系与全局基础设施（Phase 0）。
- 解锁横屏：手机和平板都允许旋转。
- 三个核心链路做完整的平板适配（竖屏 + 横屏）：**首页 → 曲库 → 播放器**。
- 底部 Tab 栏在平板下**始终贴底、贯穿全宽**，不改用侧边 Rail（这是对初版方案的修订，见 3.1）。
- 曲库在宽屏下改为「列表-详情」双栏，嵌套在内容区内部。
- **播放器在宽屏下改为常驻侧栏面板**：收起态是嵌在底部 Tab 栏行内的迷你条，展开态是从右侧铺开的竖直面板，与内容区左右并排、不整屏覆盖（这是对初版「整屏覆盖只做尺寸适配」方案的推翻，见 3.1）。
- 产出书面设计规范（本文档）+ 可交互 HTML 效果图。

### 2.2 本次不做的事

- 其余模块（搜索、歌手/MV、歌单专辑详情、播客、我的、设置、创建、云盘、消息、账号、最近播放、听歌数据、新作 feed、关注列表）的平板专项设计，后续阶段复用本文档建立的模式逐个套用。
- 折叠屏 / Chromebook 等第三档断点——只做「手机」「平板」两档。
- 平板专属性能优化、多窗口分屏专项适配。

## 3. 关键决策记录

| 决策点 | 结论 | 理由 |
|---|---|---|
| 适配范围与优先级 | 分阶段，核心链路（首页/曲库/播放器）优先 | 用户选定 |
| 是否解锁横屏 | 全面解锁（手机 + 平板都允许旋转） | 用户选定；`configChanges` 已覆盖，重建风险低 |
| 导航壳层 | Tab 组件悬浮、**不贴屏幕边缘**，**不引入 NavigationRail** | 用户参照 Spotify 平板版否决了侧边 Rail 方案（见 3.1） |
| Tab 组件与迷你播放组件的关系 | **两个独立的悬浮组件**左右并排，各自圆角/背景/阴影，不合并成一张卡片 | 用户明确否决了"合并成一张悬浮条"的方案（见 3.1） |
| 播放器宽屏展开形态 | **常驻侧栏面板**（收起=独立的迷你播放悬浮组件，展开=右侧竖直面板），与内容区左右并排，不整屏覆盖 | 用户参照 Spotify 平板版截图明确要求，推翻了「只做尺寸适配、整屏覆盖」的初版决定（见 3.1） |
| 曲库是否需要独立的列表-详情双栏 | **需要**，与「内容区+播放面板」这层双栏是两回事，两者嵌套共存 | 用户明确确认 |
| 断点触发维度 | 仅看 `screenWidthDp` 宽度，与竖屏/横屏无关 | 参考截图里竖屏、横屏平板都同时出现了「内容区+播放面板」结构，说明触发条件只和宽度够不够有关（见 3.1） |
| 目标断点范围 | 两档：手机(Compact) + 平板(合并 Medium/Expanded)，阈值 `screenWidthDp` 600dp | 用户选定；对齐 Android `sw600dp` 惯例 |
| 是否引入新 AndroidX 依赖（`material3-window-size-class`/`material3-adaptive` 等） | **不引入**，自建轻量断点工具 | 项目规范禁止未经明确指示引入新依赖 |
| UI 设计交付形式 | 书面规范 + HTML 效果图 | 用户选定 |
| 曲库 Expanded 双栏下系统返回键行为 | 清空选中回空态 | 用户选定；再按一次返回键才真正走默认系统行为（退出/切 Tab） |
| 二级页面（歌单/歌手等）Expanded 下是否遮住播放面板 | 维持整屏覆盖（含面板区域），和 Compact 一致 | 二级页面本轮不做平板专属改造（见 2.2），沿用现有全覆盖是唯一不额外增加改动面的选择 |
| `FullScreenLyricsView` 在面板语境下的展开范围 | 维持现有整屏覆盖，本轮不改 | 面板内展开需要重做歌词视图的窄版布局，超出本轮"播放器只做常驻面板结构"的范围，先按最小改动落地，体验是否割裂留到用后再评估 |

### 3.1 决策修订说明

本文档 v1 版本曾给出两个后来被推翻的方案，记录在这里避免后续阅读者困惑：

1. **导航壳层**：v1 提议「Expanded 下底部 Tab → 侧边 NavigationRail」。用户明确否决（"不用了，把底部tab栏改在底部"），改为底部 Tab 组件任何宽度/朝向下都不变。
2. **播放器展开形态**：v1 提议「播放器始终整屏覆盖，宽屏下只做尺寸/间距适配，不做结构重设计」。用户随后要求「双栏和全屏播放界面联动」，并给出 4 张 Spotify 平板版参考截图，明确展示的是「播放器收起时是一条独立的迷你播放组件，展开时是从右侧铺开的常驻面板，和左边内容区同时可见、互不遮挡」这种模式，与 v1 的「整屏覆盖」是两种不同的技术方案，本文档 v2 按此推翻重写。
3. **「竖屏套用手机的排版」这句指示的最终含义**：期间用户曾说竖屏应直接复用手机排版，一度被理解为「竖屏下和手机分辨率完全一样、没有任何双栏/面板」。但随后的参考截图显示，竖屏平板下（图2）同样出现了「内容区+播放面板」结构。结合两次澄清，现在的准确理解是：**这句指示针对的是内容区本身的结构**（首页的筛选药丸、网格、横滑区不做平板专属重设计，直接复用手机现有组件，靠可用宽度变化自然重排），**而不是否定整个应用壳层（Tab 组件、播放面板）在竖屏平板下的适配**。壳层类适配（播放面板、曲库双栏）触发条件只看宽度，竖屏横屏一致。
4. **Tab 组件与迷你播放组件是否合并**：v3 一度把两者画成"合并成一整张悬浮条"（Tab 项和迷你播放内容共用一个圆角背景）。用户明确指出"不要包裹，两个独立的组件"，v4 改为两者各自独立悬浮、并排留缝隙，不共享背景/圆角容器。

## 4. 断点体系设计（Phase 0 基础设施）

新增 `core/ui/theme/WindowSize.kt`：

- `enum class MelodiaWindowSizeClass { Compact, Expanded }`
- `rememberMelodiaWindowSizeClass(): MelodiaWindowSizeClass`：读 `LocalConfiguration.current.screenWidthDp`，`< 600` 为 `Compact`，`>= 600` 为 `Expanded`。
- `val LocalMelodiaWindowSizeClass = staticCompositionLocalOf { MelodiaWindowSizeClass.Compact }`，在顶层 `provides`。
- 不需要额外的「是否横屏」判断维度——3.1 已确认所有壳层/双栏适配只看宽度，横竖屏行为一致。

**已知边界情况**：大屏手机（横屏或竖屏宽度达到 600dp 的机型，比如部分手机横屏宽度可达 ~900dp）会被判定为 `Expanded`，出现播放面板、曲库双栏等平板样式。这是断点方法论的既定行为（度量可用宽度而非设备类型），符合业界惯例，不做设备型号硬编码排除。

## 5. 架构设计：底部 Tab 栏 + 常驻播放面板

这是本次适配里改动面最大、也是最基础的一块，Phase 0 需要先把这层壳子搭出来（面板具体内容留到 Phase 3，但容器结构在 Phase 0 就要定）。

### 5.1 整体骨架

参考截图逐像素核对后确认：播放面板展开时是**纵向贯穿整个屏幕高度**的一列（不受底部悬浮组件影响），底部悬浮组件只覆盖"内容区"这一列的宽度，不延伸到面板下方。同时用户明确要求两点：① 底部这一层**不贴边**，要像现有 `MiniPlayerCard` 一样悬浮（四周留边距、圆角）；② Tab 项和迷你播放内容是**两个独立的悬浮组件**、并排放在一起，不合并成一整张卡片：

```
┌───────────────────────────┬─────────────┐
│                           │             │
│      内容区（首页/曲库）    │   播放面板    │
│ ╭───────────╮ ╭─────────╮ │   (展开时    │
│ │  Tab 组件  │ │迷你播放组件│ │    才存在，   │
│ ╰───────────╯ ╰─────────╯ │  纵向贯穿全高） │
└───────────────────────────┴─────────────┘
   ↑ 两个独立的悬浮组件，之间留缝隙，各自圆角/各自背景色
```

收起态下没有右侧这一列，内容区占满全宽，两个独立悬浮组件仍旧并排贴在内容区底部（四周留边距、不接触屏幕边缘）：

```
┌─────────────────────────────────────────┐
│              内容区（首页/曲库）           │
│                                         │
│ ╭─────────────────────╮ ╭─────────────╮ │
│ │ Tab 组件(首页/搜索/  │ │  迷你播放组件  │ │
│ │ 音乐库/创建)         │ │              │ │
│ ╰─────────────────────╯ ╰─────────────╯ │
└─────────────────────────────────────────┘
```

- **Compact**：不变——`MelodiaNavigationBar` 悬浮贴底 + `MiniPlayerCard` 悬浮在导航栏上方（两张独立的悬浮层，垂直堆叠），`FullPlayerScreen` 点开后整屏覆盖。现状代码路径完全不动。
- **Expanded**：
  - 播放面板收起态：底部并排放着**两个独立的悬浮组件**——左边是 Tab 组件（首页/搜索/音乐库/创建 四项，沿用 `MelodiaNavigationBar` 现有视觉），右边是迷你播放组件（封面缩略图 + 歌名/歌手 + 播放/暂停，沿用 `MiniPlayerCard` 现有视觉），两者各自独立的圆角/背景/阴影，之间留可见缝隙，不是合并成一张卡片。手机上"迷你播放卡在上、导航栏在下"的垂直堆叠，在 Expanded 下变成"左右并排"。点击迷你播放组件展开为播放面板。
  - 播放面板展开态：右侧新增一列固定宽度的竖直面板（建议竖屏 ~340dp / 横屏 ~400dp，具体数值 Phase 3 结合真机调），纵向贯穿屏幕全高；内容区（含它底部的两个悬浮组件）让出这部分宽度，变成 `weight(1f)`。面板左上角有收起按钮，点击收回到迷你播放组件。
  - 顶层结构是 `Row(内容区列 weight(1f), 播放面板列 固定宽度?)`，内容区列内部是 `Box(页面内容 fillMaxSize, 底部 Row(Tab 组件 weight(1f), 迷你播放组件) align(BottomCenter) + 边距)`——两个组件用 `Box` 叠加在页面内容之上而非 `Column` 挤压布局，和现有 `MiniPlayerCard`/`MelodiaNavigationBar` 的叠放方式（`LocalBottomOverlayInset` 机制）保持一致，页面内容底部留白继续用这个既有机制计算，不用另起一套。

### 5.2 涉及文件

- `MelodiaOverlays.kt`（`MelodiaBottomOverlay`）：现有「创建菜单 + 迷你播放卡 + 导航栏」两层垂直堆叠悬浮逻辑，Expanded 下改成「Tab 组件 + 迷你播放组件左右并排，各自独立悬浮」，展开态额外渲染右侧播放面板列。
- `MainActivity` 顶层：整体从「NavHost 内容 + 底部浮层」改为「`Row(内容区, 播放面板?)`」的骨架，内容区内部沿用现有 `Box + LocalBottomOverlayInset` 悬浮浮层机制，`MelodiaWindowSizeClass` 从这里下发。
- 新增 `PlayerDockPanel.kt`：承载 Phase 3 的展开态面板内容，Compact 完全不引用这个文件。
- `MelodiaNavigationBar`/`MiniPlayerCard` 所在文件：Expanded 下各自调整为"独立悬浮卡片"尺寸（不再是手机上贯穿全宽的横条/贴顶悬浮卡），两者在 `MelodiaBottomOverlay` 里用 `Row` 并排组合，不新建合并组件。

### 5.3 二级页面的处理原则

非 Tab 页（`PlaylistScreen`/`ArtistScreen`/`SearchScreen`/`SettingsScreen` 等，除 Phase 2 曲库详情外）在 Expanded 下依然走现有「整屏覆盖 + 自带返回按钮」模式，**覆盖范围含播放面板区域**（打开二级页面时播放面板暂时不可见，退出二级页面后恢复）——已确认，理由见第 3 节决策表。

## 6. 分模块 UI 设计规范

### 6.1 首页（Home）—— Phase 1

首页内容结构**不做平板专属重设计**：`HomeSharedHeader`（头像+问候+筛选药丸）、`HomeShelfSection`/`HomeForYouSection` 横滑区、「最近播放」网格，代码结构原样保留，只是现在渲染在内容区（可能因播放面板展开而变窄的）可用宽度里，交给现有 `LazyRow`/网格组件的自适应特性自然响应：

- 若「最近播放」目前是 `LazyVerticalGrid(GridCells.Fixed(2))` 固定两列，需要 Phase 1 里确认要不要随宽度调整列数（比如按 `MelodiaWindowSizeClass` 在 2 列和 3/4 列之间切换），这是 Phase 1 唯一需要实际改代码的点，工作量比 v1 设计小很多。
- `HomeShelfSection` 的横滑区本身不需要改（`LazyRow` 天然按可用宽度显示更多/更少卡片），不用额外写自适应逻辑。
- 不改变现有动效与数据加载逻辑。

### 6.2 曲库（Library）—— Phase 2

曲库在 Expanded 下保留「列表-详情」双栏，这层双栏嵌套在内容区内部，和第 5 节的「内容区+播放面板」是两层独立的分栏：

```
│← 内容区（含曲库自己的双栏）──────────→│← 播放面板(可选) →│
│  左：歌单/专辑/歌手列表 │ 右：选中项详情 │                  │
```

- **Compact**：不变——单栏列表/网格切换，点击整屏跳转 `Screen.Playlist`/`Screen.Artist`。
- **Expanded**：新增 `LibraryExpandedLayout` 容器：
  - **左栏**（固定宽度，建议 320-360dp，具体数值需结合 6.2 末尾的三栏宽度预算风险调整）：复用 `LibraryScreen` 的列表/筛选/排序逻辑，点击不再整屏跳转，改为更新「当前选中项」状态。
  - **右栏**（占内容区剩余宽度）：渲染选中项详情，复用 `PlaylistScreen`/`ArtistScreen` 内容，需要拆出不含返回按钮/顶栏的「嵌入版」，供右栏使用（Compact 的整屏跳转路径继续用完整版，两者并存）。
  - **空态**：未选中时右栏展示居中引导态（复用 `EmptyState`）。
  - **选中态同步**：切换筛选 Tab 时，若选中项不再属于新 Tab，右栏回退空态。
  - **返回手势**：系统返回键清空选中回到空态，不直接触发默认系统行为（退出/切 Tab）；再按一次返回键才走默认行为——已确认。
- **三栏宽度预算风险**：曲库自己的双栏 + 播放面板展开态同时出现时，内容区要挤出「列表栏+详情栏」两块，平板竖屏宽度（约 800dp）减去播放面板（~340dp）后只剩约 460dp 给列表+详情，可能偏紧。这是第 7 节风险 1，需要真机验证后再定最终列表栏宽度，本文档不给死数字。

### 6.3 播放器（FullPlayerScreen 及其展开态）—— Phase 3

这是本轮从「只做尺寸适配」被推翻为结构性重做的模块，分两个状态设计：

**收起态（独立的迷你播放悬浮组件）**

- 位置：`MiniPlayerCard` 作为独立悬浮组件，和 Tab 组件（`MelodiaNavigationBar`）并排放在内容区底部——各自四周留边距、圆角、独立背景/阴影，中间留可见缝隙，不合并成一张卡片。
- 内容：封面缩略图 + 歌名/歌手（单行，超长跑马灯或截断，复用现有 `MiniPlayerCard` 里已有的取色背景/跑马灯逻辑）+ 播放/暂停按钮，和手机上 `MiniPlayerCard` 的内容完全一致，只是尺寸变成和 Tab 组件并排的窄条。
- 点击（非按钮区域）：展开为下面的面板态。
- 沿用现状：Compact 下这一状态不存在，`MiniPlayerCard` 继续单独悬浮在 `MelodiaNavigationBar` 上方（垂直堆叠的两张独立悬浮层），行为完全不变。

**展开态（常驻侧栏面板）**

结构上是现有 `FullPlayerScreen` 内容（顶部收起箭头+播放来源+更多菜单、大封面、标题/歌手/收藏、单行歌词预览、进度条、播放控件行、底部图标行、可下拉的歌词卡片）原样保留，只是把「铺满整个手机屏幕宽度的竖直排列」换成「铺在一个固定宽度竖直面板里的竖直排列」：

- 面板宽度固定（建议竖屏 ~340dp / 横屏 ~400dp，具体数值 Phase 3 真机调），内部各元素（封面方图、进度条、控件行、图标行）按面板宽度等比缩小，不是按整个屏幕宽度。
- 左上角收起箭头：点击收回到独立的迷你播放悬浮组件，而不是像手机那样"关闭播放器回到上一页"。
- 面板纵向贯穿屏幕全高（不受内容区那侧的 Tab 组件/迷你播放组件影响），和内容区左右并排，两边同时可交互（用户可以一边看面板里的播放进度，一边在左侧内容区继续翻首页/曲库）。
- `FullScreenLyricsView`（点歌词进入的沉浸式全屏歌词模式）**维持整屏覆盖**（盖住内容区和底部两个悬浮组件），不做面板内展开的窄版布局——已确认，本轮不改这块。
- Compact 下 `FullPlayerScreen` 继续保持现状的整屏覆盖，不受本节影响。

## 7. 风险与待定项

其余三项交互细节（曲库返回键行为、二级页面是否遮住播放面板、`FullScreenLyricsView` 展开范围）均已在第 3/5.3/6.2/6.3 节确认，仅剩一项技术风险留到实现阶段验证：

1. **曲库双栏 + 播放面板同时展开的三栏宽度预算**（6.2）——平板竖屏下可能偏紧，需要真机验证后再定列表栏/详情栏的具体宽度，或者约定"播放面板展开时曲库双栏的列表栏进一步收窄"之类的联动规则，具体方案留到 Phase 2/3 实现计划阶段。
2. **大屏手机（不分朝向）触发 Expanded 断点**（第 4 节）——已知行为，非缺陷。
3. `MelodiaNavHost` 的 `Screen` 路由模型是「整屏替换」心智，Phase 2 曲库内嵌详情是该模型的第一个例外，注意不要让例外模式无节制扩散。

## 8. 阶段划分与验收标准

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| Phase 0 | 断点工具类、Manifest 解锁横屏、应用壳层骨架（内容区+可选播放面板槽位 + 底部两个独立悬浮组件） | 平板模拟器下旋转不重建 Activity；Expanded 下 Tab 组件与迷你播放组件左右并排、各自四周留边距/圆角、不贴边、不合并；手机上行为与现状完全一致（回归） |
| Phase 1 | 首页 Expanded 内容自适应 | 平板下首页网格/横滑区随可用宽度自然呈现更多内容；手机不受影响 |
| Phase 2 | 曲库双栏（列表+详情），嵌套于内容区 | 平板下点击左栏能在右栏看到详情，选中态与筛选 Tab 联动正确；手机保持整屏跳转不变 |
| Phase 3 | 播放面板收起态（独立的迷你播放悬浮组件）+ 展开态（常驻侧栏面板） | 平板下可在迷你播放组件与展开面板间切换，展开时内容区与面板同时可交互；手机的悬浮迷你卡+整屏播放器行为不变 |
| Phase 4+（后续） | 其余模块逐个套用已建立的模式 | 每个模块单独设计确认后再排期 |

**测试设备**：需要至少一台真机或模拟器覆盖 `sw600dp` 以上分辨率（如 Pixel Tablet AVD），竖屏、横屏各验证一次；保留至少一台手机做回归测试。
